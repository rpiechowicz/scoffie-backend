## Co zostało do Fazy 0 (kod)

Faza 0 = fundament pod moduł `src/agent/` — zanim powstanie pierwsze wywołanie modelu:

1. **Auth REST**: iOS nie odświeża tokenu (JWT 30 dni, refresh nieużywany) → generyczny
   uwierzytelniony klient z odświeżaniem na 401 (iOS, `IntegrationsAPIClient` jako punkt wyjścia);
   backend: reuse refresh-tokenu = 401 + unieważnienie, sprawdzenie istnienia usera w `JwtAuthGuard`.
2. **Auth WebSocketu** (największy temat, osobny plan): gatewaye biorą `userId` z payloadu —
   każdy może zmienić cudze alergeny/skasować konto. JWT w handshake + pokoje per gospodarstwo;
   dopiero wtedy „które gospodarstwo” (dziś najstarsze członkostwo, `auth.service.ts buildAuthResult`).
3. **Szkielet agenta**: `src/agent/` z `AI_ENABLED=false` domyślnie, REST+JWT, 202 + polling
   (nie Socket.IO, nie SSE w v1), throttler (`@nestjs/throttler` już w zależnościach) na
   `/auth/*` i kontrolerze agenta, `catalogVersion` w digeście, zawężenie katalogu (`isCatalog` /
   `sourceProvider`), override ESLint dla `src/agent/**`.
4. **Pomiar**: prawdziwy digest katalogu przez `count_tokens` (Sonnet 5, Opus 5) — zastępuje
   szacunki w analizie; potem ewaluacja 20 promptów (Sonnet 5 low/medium/high vs Opus 5 low).
   Pozostałe FOLD-INTO-PHASE-0 / LATER z audytu: `docs/plans/weekly-meals-ai-agent/audyt/*.md`.
   Poza tym, do zrobienia po adopcji buildu B/C na obu telefonach: usunąć stub `getSavedPlan`,
   `DROP TABLE SharedMealPlan*`, gałąź `SAVE_PLAN` w iOS.

## Windows, 28.08 — krok 1 Fazy 0: auth WebSocketu + auth REST (gałąź `feat/faza-0`, backend i iOS)

- **Backend** (`src/common/ws-auth.adapter.ts`, `ws-socket.ts`, `ws-rooms.ts`, `src/auth/access-token.service.ts`):
  JWT w handshake (`auth: { token }` lub `Authorization: Bearer`) weryfikuje jeden middleware dla 5 gatewayów;
  odmowa = `connect_error` z `{code:'UNAUTHORIZED', reason: missing|invalid|expired|user_gone, requestId}`;
  tożsamość w 39 handlerach wyłącznie przez `actorId(client, payload)`; broadcasty do pokoi `household:<id>`
  (+ `legacy`), pokoje przepinane przy create/accept/leave/removeMember, `users:delete` rozłącza sockety usera;
  timer wygaśnięcia (`auth:expired` + `disconnect(false)`, klamp 2^31−1 ms); `JwtAuthGuard` na tym samym
  weryfikatorze (sprawdza istnienie usera, `details:[reason]`); refresh z reuse-detection (replay unieważnia
  rodzinę) + sprzątanie wygasłych, `POST /auth/logout`, `REFRESH_TOKEN_DAYS` domyślnie 60 (> 30 d JWT).
  `WS_AUTH_MODE=soft` (domyślne, brak zmiennej): socket bez tokenu = legacy z `payload.userId`; `strict` po
  adopcji buildu iOS — metryki `/ops/metrics.http.wsAuth` (handshakes token/legacy/rejected, legacyActs,
  payloadMismatch). Bez nowych zmiennych na Railway przed merge. `RollingTokenInterceptor` usunięty.
  Testy: 44 suites / 889 (w tym `ws-handlers-auth.spec.ts` — refleksja po 39 handlerach: anonimowy socket →
  UNAUTHORIZED, `payload.userId` obcego usera nigdy nie trafia do serwisu), e2e 17 (`test/ws-auth.e2e-spec.ts`:
  strict/soft, pokoje A/B z dołączeniem w trakcie, users:delete, logout, reuse, REST user_gone). CI e2e w `strict`.
  `pnpm ws:smoke` z `WS_TOKEN` albo `--dev-login <nazwa>`.
- **iOS** (`feat/faza-0` @ `23fad21`; bez builda — Windows; do zbudowania i sprawdzenia na Macu): `SocketIORecipeSocketClient(baseURL:tokenProvider:)`
  → `connect(withPayload: ["token"])`, `connect_error`/`auth:expired` → stop auto-reconnectu + `observeAuthFailure`;
  `RecipeSocketClient` + `observeAuthFailure/reconnectWithFreshToken/disconnect`; nowy `Networking/Auth/AuthAPIClient`
  (`/auth/refresh`, `/auth/logout`); `IntegrationsAPIClient` po 401 jednorazowy refresh + retry; `SessionStore`:
  JEDEN socket sesji (`sessionSocket()`, 21 miejsc dawniej tworzących sockety), `refreshSessionTokens()` single-flight,
  proaktywny refresh < 7 dni do `exp` (start, foreground), odmowa refreshu → logout + „Sesja wygasła”,
  `restoreSession` bez access tokenu = brak sesji, `logout()` woła `/auth/logout` i rozłącza socket.
- **Kolejność wdrożenia**: backend (soft) → iOS na TestFlight → oba telefony → `WS_AUTH_MODE=strict` na Railway.

## Windows, 28.08 — krok 2 Fazy 0: walidacja wejścia WS i in-process (gałąź `feat/faza-0`; backend `a5e9ccd`, iOS `2f2af36`)

- **Dlaczego**: dekoratory class-validator na DTO były na WS martwe (globalny `ValidationPipe` = tylko HTTP;
  pipe na gatewayu rzuca PRZED handlerem i omija ack). Zły enum/typ → `PrismaClientValidationError` 500,
  nie-UUID → P2023 500, brak `data` → TypeError 500, nieznany `mealType` w filtrach = cały katalog. Asystent
  Fazy 1 woła te same serwisy in-process, więc walidacja musi siedzieć W SERWISACH.
- **Fundament** (`src/common`): `validateDto(cls, plain)` na `ValidationPipe` (ten sam pipe i format
  `details`, co HTTP — test parytetu przez `mapError`), `validateWsPayload` (koperta: whitelist bez forbid —
  stare buildy), `isUuid`/`assertUuid` (jedna definicja = validator.js `all`, jak `@IsUUID()`), P2023 →
  VALIDATION_ERROR, `APP_ERROR_CODES as const` (+ `INGREDIENT_NOT_FOUND`, `SHOPPING_LIST_ARCHIVE_NOT_FOUND`,
  `SHOPPING_ITEM_NOT_FOUND`), `maxHttpBufferSize` 256 KB, legacy `payload.userId` nie-UUID → UNAUTHORIZED.
- **Wzorzec** (obowiązuje każdy nowy handler/serwis; opis w `CLAUDE.md`): handler = `actorId` → `await
validateWsPayload(Koperta, payload)` (każde pole koperty MA dekorator; `data`/`filters` tylko `@IsObject`);
  serwis = `dto = await validateDto(Dto, dto)` na wejściu (strict whitelist), skalarne id przez `assertUuid`
  w bramkach (`ensureMembership`, `getHouseholdOrThrow`, `ensureRecipeForHousehold`); DTO z enumami Prismy
  (`@IsEnum(DayOfWeek)`, `MembershipRole`, `Difficulty`, `Sex`, `PushPlatform`), `@IsUUID()` na id.
- **Zmiany kontraktu** (iOS zgodne — audyt payloadów: klient wysyła dokładnie pola DTO, natywne liczby/bool):
  `weeklyPlans:getByWeek` pustego tygodnia = pełny pusty plan (wiersz tworzony przy odczycie, P2002 → ponowny
  odczyt; iOS dekoduje `id`/`weekStart` jako wymagane), `weekStart` w odpowiedzi `'YYYY-MM-DD'`; item planu
  niesie `allergens/dietTags/suitableMealTypes` (iOS: koniec heurystyki w planie); `setMealEaten` bez planu →
  `PLAN_ITEM_NOT_FOUND`; `recipes:findAll` z nieznanym `mealType` → VALIDATION_ERROR (nie cały katalog);
  `recipes:create` z nieznanym składnikiem → `INGREDIENT_NOT_FOUND` z `details` = brakujące id (+ naprawiony
  realny błąd: `ingredientId` WIELKIMI literami z iOS chybiał mapę i dawał TypeError 500);
  `notifications:registerDevice` ma DTO (`RegisterDeviceDto`), pusty token → VALIDATION_ERROR; `setFavorite`
  broadcastuje zwalidowane dane (serwis zwraca `{recipe, change}`, ack bez zmian). Limity, które na WS
  zaczęły działać dopiero teraz (stare buildy iOS dostaną VALIDATION_ERROR z generycznym komunikatem):

- **Testy**: `ws-handlers-validation.spec.ts` (fixture `src/common/ws-payload-fixtures.spec-helper.ts`:
